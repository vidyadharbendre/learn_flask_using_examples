Autoescaping, |safe, and why order matters

The variable hostile is the string <script>alert('xss')</script> Bobby <b>Tables</b>. Below it is rendered four ways. View source to see the difference in the bytes actually sent to your browser.

1. Default — autoescaped (safe ✅)

{{ '{{ hostile }}' }}
{{ hostile }}

Jinja converted < to &lt;. The script tag is displayed, never executed. This is the default for .html templates and it is why Flask apps are XSS-resistant out of the box.

2. |e — explicit escape (safe ✅, redundant)

{{ hostile|e }}

Harmless but unnecessary; |e is already implied.

3. |safe on untrusted input (DANGEROUS ❌)

{{ '{{ hostile|safe }}' }}
{{ hostile|safe }}

That box just executed an alert-shaped payload — the <b> renders bold and the script tag was injected into your DOM. Never apply |safe to anything a user typed.

4. Markup(...) produced by our own code (safe ✅)

{{ trusted }}

trusted was wrapped in Markup() inside app.py. It is safe because we wrote it, not because we called |safe.

5. The right way to emit HTML around user input

The highlight filter escapes first, then adds its own <mark> tags, then returns Markup:

{{ hostile|highlight('bobby') }}
The rule: escape untrusted input first, add your trusted markup second, and mark the result safe last. Building a string and slapping |safe on the end is how XSS vulnerabilities are written.
